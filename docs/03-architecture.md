# Архитектура

## Решение

Модульный монолит с чистым детерминированным ядром. Правила не зависят от DOM, HTTP, хранилища или конкретного интерфейсного фреймворка. На первом этапе — JavaScript ESM и встроенный тестовый раннер Node.js: ядро работает одинаково в браузере и тестах, без внешних зависимостей. До расширения карточного DSL целесообразно добавить строгую проверку типов; перенос на TypeScript не меняет границы.

```text
apps/web (представление, действия пользователя)
       ↓
packages/application (сеанс, команды, порты сохранения)
       ↓
packages/domain (состояние, правила, эффекты, RNG)

packages/adapters (localStorage, позже HTTP/SQLite/Postgres)
       → реализуют порты application
packages/content (данные контент-пакетов)
       → передаются в ядро через композицию приложения
```

Домен ничего не импортирует из остальных слоёв. Контент не содержит UI и сетевых функций. Адаптер сохранений можно заменить памятью в тесте. Настоящий сервер будет использовать тот же домен; доверие клиентскому состоянию недопустимо.

## Состояние и команды

Основные фазы новых партий: `auction → settlement → planning → production → следующий auction | finished`. Полная версия дополнит их подготовкой, размещением управляющих и вложенными решениями. Обработчик `dispatch(state, command, definitions)` проверяет команду, клонирует состояние и возвращает новое. При ошибке исходное состояние неизменно. Время и случайность из окружения в него не попадают.

`ArrangeCards` проверяет полную перестановку принадлежащих игроку карт. При productionChain=true подпоследовательность lockedOrder (зафиксирована в начале аукциона) не может изменяться. `ConfirmPlan` переключает планирующего; после всех подтверждений начинается производство. В цепочке UseCard принимает только первую ещё не использованную карту. В начале следующего раунда новые карты становятся частью lockedOrder.

`packages/application/decision-clock.mjs` содержит рекомендательный таймер с внедряемым now. Ключ решения отделяет ставку/компенсацию от этапа планирования/производства. Deadline сохраняется в record.clock, за пределами детерминированного журнала команд. Истечение ничего не отправляет в domain. Версия правил prototype-0.2; legacy prototype-0.1 восстанавливается с planning=false, productionChain=false, turnSeconds=0, чтобы не менять ход старой партии посреди replay.

На первом этапе реализуются `Bid`, `ResolveLot`, `Compensate`, `UseCard`, `Convert`, `NextEffect`, `Upgrade`, `FinishProduction`. Пропуск обязательной добычи не представлен командой: она обрабатывается автоматически в её очереди. Количество переработок выбирает человек. Завершение карты закрывает возможность вернуться к её предыдущим строкам.

В каждом решении хранится игрок, которому оно принадлежит; это может быть проигравший аукцион, а не очередной участник торгов. Лоты имеют стабильный порядок. Выигрыш карты происходит только после компенсаций. На будущее вставка поставки/реакций выполняется до перехода к следующему лоту.

## Полная модель эффектов (следующие этапы)

Декларативные виды: `gain`, `convert`, `upgrade`, `supply`, `trigger`, `countCards`, `repeat`, `copyNeighbor`, `discardSelf`, `localResource`, `choice`. У каждого — фаза, область, обязательность, лимит, условие активной стороны и provenance.

`convert` исполняется по одной операции: проверить/списать вход → выдать выход → сформировать событие `ConversionPerformed` с признаками sale/exchange → разрешить реакции → следующая операция. Простой умножитель кошелька неверен для дополнения. Постоянные модификаторы лимитов и реактивные выплаты не смешиваются.

`EffectFrame` хранит карту, сторону, строку, оставшийся лимит, локальные ресурсы и возврат к прерванному контексту. `PendingChoice` содержит допустимые варианты и actorId. Копирование не меняет собственника оригинала. После повтора цепочка возобновляется с сохранённой позиции. Поставки и улучшение не обнуляют usedRound.

Не писать один универсальный текстовый интерпретатор. Каждая подтверждённая особая способность получает именованный обработчик и сценарий. Неподдерживаемый вид эффекта должен отклоняться, а не игнорироваться.

## Модули правил

`RuleConfig`: base/interbellum companies, capitalists, managers, variableCapital (off/coal/round), productionChain, humanCount, agentPolicies. Валидатор конфигураций исключает несовместимые карты до раздачи. Состав колоды строится отдельной функцией с seed. Идентификатор семейства обязателен для выбора двух из трёх базовых предприятий.

Промышленник с двумя одновременными ставками требует одной атомарной команды с двумя целями. Частичное применение недопустимо. Промышленник без ограничений изменяет только оговорённые проверки ставки и правило ничьей, не отключает валидацию целиком.

## Хранение и replay

В прототипе localStorage содержит версионированный seed + принятые команды, а состояние восстанавливается повторным применением команд. Повреждённый журнал не заменяется автоматически новым. UI сообщает ошибку; пользователь может явно начать новую партию.

Для сервера: таблицы games (версии, seed, revision, snapshot), seats (session/actor), commands (уникальный gameId+commandId), events (gameId+seq), content_packs. Обновление состояния и запись команд выполняются в одной транзакции с optimistic concurrency. Снимок ускоряет чтение, журнал позволяет расследовать ошибки. Старые игры закреплены за версиями правил/контента.

## Безопасность и тестируемость

Внешняя граница проверяет структуру/размер входа, домен — смысл. На сервере actorId берётся из подтверждённого места, а не из поля запроса. Наружу выдаётся специально построенная проекция состояния. Ошибки не раскрывают колоду, RNG или чужие сессии. Пользовательские имена выводятся как текст.

Тесты домена охватывают решения и переходы, а не HTML. Тест полного четырёхраундового прогона проверяет возможность завершения, ротацию и неотрицательные запасы. Отдельные тесты на replay и недопустимые команды защищают сохранения. UI-проверка нужна для игрового действия и мобильной раскладки.

## Чего пока нет

Первый этап не реализует университеты, управляющих, поставки, постоянные/текстовые способности, промышленников, официальных агентов и сетевой сервер. Их интерфейсные границы описаны, но нельзя считать их работающими. Цепочка добавлена 28.09.2026 на учебном контенте. Учебный переключатель переменного капитала проверяет только этот модуль с дополнительным лотом; он не называется полной поддержкой Интербеллума.
